# kimi-tide 定位与维护策略

> 一份诚实的自我定位声明：这个项目是什么、不是什么、哪些部分会被时间淘汰、哪些部分值得长期投入。
> 写于 2026-08，背景是项目发布后的第一次战略审视（对照 Open Design 等生态项目）。

---

## 1. 一句话定位

**kimi-tide 是 DSH 生态的模型接入与互补分工层，不是应用。**

- Open Design 是**应用**（回答"怎么用 AI 做设计"），kimi-tide 是**基础设施**（回答"怎么在 DSH 里用 Kimi、怎么让两个模型分工"）
- 两者不竞争：Open Design 可以是 kimi-tide 的用户——它启动 DSH 后，kimi-tide 让 DSH 多一个 Kimi 模型可选
- 与 `dsh-kimi-bridge` 的分工：bridge 把 Kimi CLI 当**外部进程**调（独立 agent 会话），kimi-tide 把 Kimi 当 **DSH 内一等模型**（与 DeepSeek 平级）

## 2. 与 Open Design 的区别（对照表）

| 维度 | Open Design | kimi-tide |
|------|-------------|-----------|
| 层次 | 应用层（垂直：设计/原型/PPT/视频） | 接入层（水平：模型 + 路由） |
| 用户 | 做设计工作流的人 | 在 DSH 里做任何事的人 |
| Kimi 的角色 | 26 个可选引擎之一，外部子进程（`kimi acp`） | DSH 内一等模型，可切换、可路由 |
| DSH 的角色 | 运行后端之一 | 宿主平台 |
| 合规性 | ✅ 官方 ACP 协议 | ⚠️ token workaround（文档化风险） |
| 核心问题 | 设计产物生成 | 模型接入 + 互补分工 |

## 3. 项目价值的三层拆解（按"官方替代性"排序）

| 层 | 内容 | 官方会替代吗 | 策略 |
|----|------|-------------|------|
| **接入层**（0.1.x token 方案） | pi-ai 适配 + OAuth token 轮换 | **会**——DSH 出 OAuth/ACP 支持即退役（`dsh-subagent-acp` 已在 npm，只是尚无 rc.6 配套版） | **冻结维护**：保持可用，不投新功能，不在这层加码 |
| **分工层**（0.2.0 路由器计划） | cost/capability 路由、能力缺口补偿、预算控制 | **不会**——"谁的任务用谁的模型"是策略，官方只提供机制，不替你决策 | **长期投入**：项目真正的核心价值 |
| **方法层**（协作闭环文档） | 审查-修复-复检流程、踩坑档案、模板 | 不会，且与项目存亡无关 | **持续沉淀**：独立价值 |

**一句话策略**：别在租来的时间上盖楼，把砖都铺到自己的地上。

## 4. 诚实清单（项目的边界与灰区）

- ⚠️ token 方案是条款灰色地带（Kimi Code 订阅"仅限个人交互式使用"），个人量级低风险；完全合规路径是开放平台 API key 或官方 ACP
- ⚠️ 单插件规模（1 star）、单人维护，不承诺长期支持
- ✅ 不依赖任何闭源组件、凭据零入库、全链路可复现
- ✅ 审查闭环与踩坑档案对 dsh-plugin 生态早期有真实参考价值

## 5. 维护策略与退役计划

| 事件 | 行动 |
|------|------|
| 日常 | 冻结接入层、投入分工层、沉淀方法层 |
| `dsh-subagent-acp` 发布 rc.6 配套版 | 路由器迁移到 ACP 通道，token 方案退役（README 标注 legacy） |
| DSH 原生支持 OAuth | 同上，接入层整体删除 |
| DeepSeek V4 后续版本支持多模态 | 路由器的"图片补偿"改为能力检测（查 `inputModalities`），自动跳过补偿 |

## 6. 项目的时间观

kimi-tide 是**过渡期方案**：它在官方能力到位的窗口里提供真实价值（今天唯一能让 Kimi 成为 DSH 模型的路），并在窗口关闭时把可迁移的资产（路由器、方法论）带走。一个知道自己会死的项目，反而能清楚知道什么值得活着做下去。
