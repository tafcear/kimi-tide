## 1. 背景与根因

**现象（用户实机，两类同源故障）**：

- **漏命中（假阴）**：`~/.dsh/settings.yaml` 的 `saving` 预设**只有一条规则** `code-kfc`（`code` 组 → `zai-coding-cn/glm-5.3`）。用户说「帮我看看这段有没有问题」——`code` 组 17 词（`config.ts:99`）一个都没出现 → 规则链空 → 整轮落打底 `deepseek-official/deepseek-flash`，编码任务交给打底模型。
- **误命中（假阳）**：1.1.0 之前的实机原案——「这个做完做交叉评审」被 `review` 组（`评审`）整轮劫持到评审模型，执行工作被错误改道（`2026-09-02-review-flow-design.md` §1）。

**根因**：`matchingScored`（`rules.ts:104-124`）是**纯词法**判定——子串/词边界匹配，引擎里没有任何东西能回答「这个词在这句话里是不是这个意思」。两类故障是同一个缺口的两个方向。

**为什么现在做**：路由层解决的是「这句话该由谁答」，而判定这句话意图的成本，**比把这句话答砸的返工成本低一个量级**；且判官恰好是「本来就要干这活的那个便宜模型」，增量≈同一档位多一次极短调用（§4 成本账）。

**为什么不是改关键词表**：加词解决不了假阳（「评审」既是名词也是动作），减词解决不了假阴（同义表达无穷）。词表调参是把语义问题伪装成枚举问题。

### 1.1 与已有机制的关系

| 机制 | 关系 |
|---|---|
| 1.1.0 被认领组的静态抑制 | **正交、先于本闸**：认领抑制是「配置即事实」（无条件、与本轮无关），本闸是「本轮文本语义确认」（逐轮）。判官只在**抑制后**剩下的 routable 命中上工作。 |
| 评审流武装 `reviewTriggerHit` | **本版不接**（§2.2）。武装语义与路由语义相邻但不同物，接线时机留待实测。 |
| `previewRoute` 试一句 | 浏览器侧无 LLM 通道 → 无法等同预演（§8.2，**必须显式标注偏差**）。 |

## 2. 闸门语义（本设计的核心，逐条钉死）

### 2.1 位置

决策链仍是 `decide()` 的既有四段（`router.ts:231-292`）：

```
显式 @ 指令  →  [认领抑制]  →  【本闸：逐条确认】  →  规则链首个可用目标  →  预设默认打底
```

`decide()` **保持同步纯函数**——语义结果由 `installRouter` 的 pre-step（本来就是 `await` 点，`router.ts:579` `async (payload, next) => { await next() ... }`）预计算，`decide` 只多收一个「已否决集合」入参。

### 2.2 闸门的作用对象

- **确认范围 = `when.kind === 'keywords'` 的命中**（认领抑制之后）。
- **image 命中不过闸**：图片是客观事实，没有「语义真伪」可判。用户裁定「关键词命中时才判断」的字面落地就是这条。
- **被认领组不进闸**（第 1.1 节的顺序）——被抑制的规则不参与路由，也不产生判断调用。
- **显式 @ 不进闸**（`decide` 第一段就短路，先于规则链；与 1.1.0 保持同向）。
- **已知取舍（记入本版限制）**：`hasImage` 为真时 `image` 命中分 `∞` 恒排第一，关键词规则会被排在后面——本闸不改这个序，故「带图轮的关键词命中」几乎并不发生。不修，留 -next。

### 2.3 判定内容

判官拿到的是「**用户本轮文本 + 候选规则的组名与目标**」，输出三态：

| 输出 | 含义 | 路由后果 |
|---|---|---|
| `hit` | 这些词确为本轮意图 | 该规则照常参与规则链 |
| `omit` | 这些词不是本轮意图（提及/引用/延后语境） | **跳过该条规则，继续后续规则**（用户裁定 #3） |
| 无结论（超时/不可用/解析失败） | 判不了 | **不过闸**（fail-open，§4.4） |

判否**不产生新目标**：目标仍然只能来自规则表，语义只做「是/否」，不做「改判到哪」。这是「判官永远比关键词弱一层权限」的护城河——语义层不可能把请求送到用户没配过的地方。

### 2.4 明确的能力边界（防过度解读）

闸门读的是**本轮用户文本**，不是「模型接下来的动作」。因此它**能**治 §1 的两类故障，**不能**治：

- 模型在 step 1 之后改变做法（用户说「先看看」模型直接改文件）—— 需要轨迹/工具信号，属动作层，本版不做；
- 关键词零命中的语义兜底 —— 属假阴的另一半（本版只做假阳侧确认；假阴侧见 §11.2 待议）。

### 2.5 判否与既有降级路径的关系

**判否 ≡ 与「目标在候选目录不可用」完全同型**：都走 `decide` 循环里的 `continue`（`router.ts:275 / 278 / 282 / 286`），都落在同一个打底出口（`router.ts:291`）。这不是新语义，是把既有降级路径多接了一个来源——实现的正确性标准即「被否的规则等同不存在」。

## 3. 调用契约

### 3.1 目标模型

**判官 = 当前激活预设的 `preset.default`**（用户裁定 #2）。三个后果，全部为设计意图：

1. **成本与档位自洽**：saving 预设的 default 是 `deepseek-flash` → 判官就是那个本来要干活的便宜模型。
2. **判官可用性天然满足大半**：默认模型是打底出口，宿主目录里没有它时规则链本身已经失去意义。
3. **必须记入限制**：若用户把 default 配成贵模型（capability 预设的 default 是 `k3`），确认闸的成本按 default 档位计——**便宜打底 + 贵规则**才是本闸的经济形态。

### 3.2 走哪条通道（防递归）

`ctx.llm.stream(options)` 直调，`options` 显式带 `provider/model`，**不经** `agent/request` / `llm/stream` 的既有拦截路径（与 `review.ts:81-88` 同型）。三条保证：

- 判官调用不进 `decide`，不与本轮路由决策形成先后依赖；
- 不与 `auxTargets`（0.8.x⑧，envelope `purpose` 驱动）互相干扰——**判官调用不设 `purpose`**；
- 投影拦截器（`llm/stream` 的转述替换）不改写它——纯文本无图块。

### 3.3 输入构造（`buildConfirmInput`，纯函数）

```
[系统指令] 你是路由确认器。下面这些词在用户这句话里，是不是本轮真要执行的意图？
          只输出一行 JSON：{"verdict":"hit"|"omit","rule":"<规则id>"|"omit","why":"≤20字"}
          只有引用/转述/延后语境（如「这个做完再做X」「你上次说的X」）才算 omit；不确定一律 hit。
[用户本轮文本]
<text，≤600 字符截断并标注>
[候选规则]
- rule-abc｜组 review｜目标 kimi-coding/k3
- rule-def｜组 code｜目标 zai-coding-cn/glm-5.3
```

- 组名与目标可见，**词表不进 prompt**（控 token）；
- 候选表上限 8 条（超出按路由链序截断并记日志）；
- 输出上限 `maxTokens`（缺省 32，配置可调）——一行 JSON 足够。

### 3.4 输出解析（`parseConfirmVerdict`，纯函数）

- 剥离 ``` 代码块围栏、容忍前后空白与大小写；取首个 `{...}` 做 `JSON.parse`；
- `verdict` 非 `hit/omit`、`rule` 不在候选表内、JSON 解析失败 → **返回 null = 无结论**（保守通过，绝不误否）；
- **不要求**判官输出与输入规则数一一对应：一条 verdict 一个规则（多命中时只判路由链首条，见 §4.5 成本控制）。

### 3.5 超时与中止

- 有界超时 `timeoutMs` 缺省 **1200ms**（配置可调）；
- 信号 = `AbortSignal.any([turnSignal, AbortSignal.timeout(timeoutMs)])`，复用 `boundedSignal` 的退化链（`router.ts:368-373`：无 `AbortSignal.any` 的宿主退化为 turn 信号）；
- 超时即 `abort` 该次流，**不排队、不重试**，不阻塞本轮（判官是「问一句」，不是「必须答」）。

### 3.6 失败退化（fail-open）

| 情形 | 行为 |
|---|---|
| 判官目标不在候选目录 / `available === false` | 不过闸（跳过确认），日志记因 |
| 流失败 / 空输出 / 解析失败 / 超时 | 不过闸 |
| 本轮无关键词命中 | 不调用（零成本路径，行为与 v1.2.1 逐字节一致） |

**为何保守通过而非保守否决**：判官缺失/超时说明「问不到」，与「问到了说不是」是两件事。问不到就按词法结果走，语义层**永不制造比现状更坏的结果**。

### 3.7 缓存

- 键 = `normalizeText(用户文本) + '\u0000' + 候选签名`（`ruleId:group:targetKey`，按路由链序拼接）；
- LRU cap 64（与 `Transcriber` 的 `DEFAULT_CACHE_CAP` 同量级，`transcribe.ts:38`）；
- **只缓存「有结论」的结果**，失败/超时不写缓存（否则一次网络抖动会被缓存 64 条）；
- 缓存命中不发调用，`durationMs = 0` 记日志。

### 3.8 观测

单条 `ctx.logger.info`，格式固定（实施时写死契约，测试断言此串）：

```
kimi-router: 语义确认 <provider>/<model> <durationMs>ms textLen=<n> → < verdict | 无结论(原因) >
```

面板决策原因（§8.3）走既有 `DecisionSummary.reason` ≤120 截断契约。

## 4. 成本账（本版必须写进 README 的既有「非目标」位置）

`router.md:541` 把「LLM 语义分类」列为 0.8.0 非目标，理由是成本 + 延迟。本版把它做成**有条件、可关闭**的形态，账目如下：

| 场景 | 增量 |
|---|---|
| 关键词未命中轮 | **0**（不调用） |
| 关键词命中、判官确认 | 1 次极短调用（prompt ~300 token 级，输出 ≤32 token）+ ≤1.2s 等待 |
| 关键词命中、判官判否 | 同一次调用 + 本轮落打底（**省下的是「不该改道却改道」的整轮返工**） |
| 缓存命中 | 0 |

**延迟位置的既有先例**：pre-step 已经是整轮的阻塞点（eager 转述默认 30s 上限，`router.ts:361`）。1.2s 的确认预算在同一量级之下；且**超时即放弃**，不会成为「不可用即挂死」的新黑洞。

**每轮至多一次调用**：pre-step 的 `payload.step !== 1` 门控（`router.ts:588`）保证只在本轮首个模型步判定；工具循环步骤不切模型、也不再判断（「一轮一判」语义保持）。

## 5. 路由层改动（`rules.ts` / `router.ts`，纯函数面）

### 5.1 新增纯函数（`rules.ts`）

```ts
/** 可确认的命中：认领抑制之后、kind==='keywords' 的命中（按路由链序）。 */
export function confirmableHits(config: RouterConfigAny, hits: readonly RuleMatch[]): RuleMatch[]

/** 应用确认结果：verdict 为 omit 的规则从链中剔除；无结论/未覆盖的规则原样保留。 */
export function applyConfirmVerdicts(hits: readonly RuleMatch[], omitted: ReadonlySet<string>): RuleMatch[]
```

不引入新的命中语义——两个函数都是**过滤**，可单测、可证伪。

### 5.2 `decide()` 签名扩展

```ts
decide(messages, step, hasImageOverride?, omittedRuleIds?: ReadonlySet<string>): RouteDecision
```

- `omittedRuleIds` 缺省为空集 → 行为与 v1.2.1 **逐字节一致**（存量调用点、试一句、全部旧测试不动）；
- 剔除发生在认领抑制之后、循环之前；
- **被否规则不进 `hits` 原文**：`hits` 本身保留全量（观测/试一句口径），只有路由链 `routable` 被过滤——与 1.1.0 的「原文保留、路由链过滤」同构（`router.ts:254-257`）。

### 5.3 原因文案

判否会改变既有断言串（`router.test.ts` 的 `规则「code」命中 N 词` 系列），**变化必须显式登记**：

| 情形 | 原因 |
|---|---|
| 未过闸（配置关 / 判官不可用 / 无结论 / 缓存未覆盖） | 不变：`规则「code」命中 2 词` |
| 判官确认后生效 | `规则「code」命中 2 词 · 已确认` |
| 判否后落打底 | `规则「code」命中 2 词 · 语义判否 → 预设「省钱」默认` |
| 判否后命中次条规则 | `规则「math」命中 1 词 · 前序判否` |

（均受 `DecisionSummary.reason` ≤120 截断契约约束。）

## 6. 配置（`config.ts` / `settings-schema.ts`）

无版本升级（v5 保持），新增字段**全部可选、缺省省略**，与 `imageFallback`/`imageFallbackFlow`/`auxTargets` 同款兼容策略（`settings-schema.ts:75-80` 的既有注释即依据）：

```ts
/** 预设级语义命中确认闸（v1.3.0）。缺省 = 关闭（存量行为零突变）。 */
export interface HitConfirm {
  enabled?: boolean
  timeoutMs?: number   // 1..10000，缺省 1200
  maxTokens?: number   // 1..256，缺省 32
}
// RouterPreset 增：hitConfirm?: HitConfirm
```

- `DEFAULT_CONFIG_V5()` **不带** `hitConfirm`（预置预设不开启）——**存量用户升级后行为零突变**，开启是显式动作（与 1.1.0「预置 review 流保持 manual」同款裁定逻辑）；
- `settings-schema.ts`：`presetSchema` 增 `hitConfirm: Schema.object({ enabled: Schema.boolean(), timeoutMs: Schema.number(), maxTokens: Schema.number() })`（对象型字段缺失即注 `{}` 的既有行为 → 语义上等同关闭，无副作用）；
- `validateRouterConfig` 增校验：`timeoutMs`/`maxTokens` 存在时须为整数且在界内（越界文案带预设 key，与既有风格一致）。
- **为何不放全局而放预设**：判官就是 preset.default，确认行为与预设绑定才自洽；全局开关会与「判官属于哪个预设」打架。

## 7. 编排层（`installRouter`，`router.ts`）

执行序（插在现有 3「决策」段，`router.ts:613` 附近）：

1. `hits = matchingScored(...)`；`claimed` 抑制 → `routable`；
2. `gate = preset.hitConfirm`；`enabled !== true` **或** routable 里无 keywords 命中 → 走 v1.2.1 原路径（零调用）；
3. 候选签名 + 文本 → 查缓存：命中 → 直接取 verdict；
4. 查判官可用性（`router.metas` 里 default 的 `available`）；不可用 → 记日志 + 不过闸；
5. `confirmableHits(...)` 取**路由链首个**待确认规则（§4.5）→ `ctx.llm.stream` 一次（§3.2-3.5）→ 解析（§3.4）；
6. 组装 `omittedRuleIds`（本轮至多一个元素）→ 写缓存（仅成功）→ 记日志（§3.8）；
7. `router.decide(payload.messages, payload.step, hasImage, omittedRuleIds)`；
8. 其后全部既有分支（eager/lazy 转述、imageFallback、评审武装、槽位、`onDecision`）**一律不动**。

**依赖注入**：新增 `RouterOrchestrationDeps.hitConfirm?: { call: ConfirmCaller; cacheCap?: number }`——生产由 `index.ts` 组装（`ctx.llm.stream` 直调 + `log`），测试注入假 caller/小超时，与 `transcriber` 同款缝（`router.ts:339-346`）。

## 8. UI 与可解释性

### 8.1 设置卡片（`SettingsCard.tsx`）

- 预设编辑区新增「语义命中确认」折叠块：`enabled` 开关 + `timeoutMs` 数字 + `maxTokens` 数字 + 说明文案（含「判官 = 本预设默认模型；判否=跳过该规则继续后续规则；超时/失败按原关键词结果」）；
- a11y：三个控件的可访问名带预设名（既有一行规则「第 N 条·条件」的正面参照，`_ui-review-2026-08-29.md` P2-7）；
- 写入期校验：越界即拒存（与既有 minHits/rounds 同款策略）。

### 8.2 「试一句」预演（**必须标注偏差**）

浏览器侧拿不到 LLM 通道，`previewRoute` **不模拟**确认闸。处置：

- `RoutePreview` 增可选 `hint?: 'confirm-gate-on'`（本预设开启且文本命中 keywords 时置位）；
- 卡片固定声明追加一句：「实际路由还取决于语义确认（浏览器侧无法预演）」；
- **不允许**给用户「预演 = 最终结果」的错觉（这是本版最容易产生的可解释性倒退）。

### 8.3 决策观测

- 面板 chip：`规则「code」命中 2 词 · 已确认` / `· 语义判否 → 打底`（§5.3）；
- dock 流事件行沿用 `onDecision` extra 通道，可携带 `confirm:ok|omit|fail`（≤120 截断）。

## 11. 未决与后续

1. **判官调用可否预取**：目前只能在 pre-step 同步等（下一轮的消息在轮末还不存在）。若实测 p95 延迟不可接受，备选是「判官先答、路由后调」，但会把模型切换推迟到 `agent/request` 之后——需重新评估。
2. **假阴侧（关键词零命中）的语义兜底**：本版不做。若做，必须是「只在无任何规则命中时才问判官」，否则回到「每轮一次 LLM 调用」的成本模型（0.8.0 非目标的原始理由）。
3. **动作层**（按轨迹/工具判「接下来做什么」）：与本文的文本层是两件事，独立设计。
4. **评审流武装是否接同一闸**：本版不接，留待 A3 实机数据（判否率）出来后再定。
5. **判否率指标**：实施时把 `confirm:omit` 计数暴露到 dock/日志，用于判断「这闸该不该默认开」。
