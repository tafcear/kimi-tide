## A. 0.1.7 插件配置/设置的正道

**结论一句话：0.1.7 的 `ctx.settings` 是从「插件 Config schema」投影出的**表单服务**，插件侧唯一合法用法是 `configure()`；配置节不是插件「注册」出来的，而是**当前 profile 里那条 loader entry 本身**，其 id 就是 `ns`，其 `Config` schema 就是表单来源；插件运行时读自己的配置一律走 `ctx.config`（cordis 注入的 Config 引用），不经过 settings 服务。**

### A.3 插件如何「声明自己的配置节」——不是 package.json、不是 cordis.patch.yml 单独的东西

三条路径的真实分工：

1. **`package.json` 的 `dsh` 字段 = 客户端装配声明，与配置节无关。**
   `<PLUGIN>\package.json:41-52` 的 `dsh.bundle` / `dsh.client` 只声明「bundle patch 文件是谁」和「客户端半链要 inject 哪些包」。
2. **`cordis.patch.yml` = 组合入口层**，它决定 entry 的 `id`/`name`/`config`。
   `<PLUGIN>\cordis.patch.yml:7-13` 插入 `id: dsh-kimi-tide, name: dsh-kimi-tide, config: {}`。
   **这个 `id` 就是 0.1.7 的 `ns`。**
3. **插件的 `Config` 导出 = 配置节的形状（唯一的形状来源）。**
   `<HOST>\dsh-settings\lib\index.js:538-541`
   ```js
   schema(entry) {
       const schema = entry.fiber?.runtime?.Config;
       return schema !== undefined && "toJSON" in schema ? schema : undefined;
   }
   ```
   而 `<HOST>\dsh-settings\lib\index.js:122-131` 的 `volatileForm(schema)` 要求：**schema 本身或它的某个 object 子节点带 `.volatile()` 元数据**，否则这个 entry **根本进不了表单**：
   ```js
   function volatileForm(schema) {
       if (schema.meta.volatile) return plainSchema(schema);
       if (schema.type === "object") { /* 递归找带 volatile 的子字段 */ }
   }
   ```
   → **没有 `Config` schema、或 schema 里没有任何 `.volatile()` 字段的插件条目，会被 `describe()` 直接跳过，UI 里看不到任何配置节。** 这正是 kimi-tide 现状（见 A.5）。

## E. `agent/created` / `agent/disposed` 在 0.1.7 的正确写法

**结论一句话：`agent/created` 是 `@mode serial`（监听器被逐个 await，返回值被当作 bail 值检查），签名是 `(this: Scoped<Agent>, payload: { agent; source; signal? }) => undefined | Promise<undefined>`；`agent/disposed` 是 `@mode emit`（同步、不等 Promise）。kimi-tide 的现有写法「恰好能编译」，但返回 `undefined` 是硬要求，且「不得 await 自身清理」是文档级约束。**

### E.1 声明原文

## H. `Message` / `RequestMessage` / `RequestUserInput`

**结论一句话：`Message` 是**持久化会话消息**的联合（必有 `id` 与 `source`），`RequestUserInput` 是**只在单次请求里有意义**的 user 输入（`id?: never` 且 `source?: never`，用类型把「不可能有身份」写死），`RequestMessage = Message | RequestUserInput` 是请求面接受的并集；插件把 `RequestMessage[]` 塞给 `readonly Message[]` 的地方**在 0.1.7 下应当泛化成「只要求有 content」——插件 `src/router.ts` 已经这么做了。**

### H.1 三者的原文定义

`<HOST>\dsh-llm\lib\types\types.d.ts:467-475`

```ts
    readonly source?: never;
```

```ts

    /** Stable identity preserved across every representation boundary. */

     * @persistenceSource user developer */
    readonly source: MessageSource;
```

`<HOST>\dsh-llm\lib\types\message.d.ts:161-174`

**「`RequestUserInput` 为何没有 `id`」的权威答案**：三条证据合起来看 —
1. 类型注释本身：`/** User input for one LLM request; **it has no durable Session identity or source**. */`（`types.d.ts:467`）。
2. `id?: never` / `source?: never` 是**刻意的反向约束**：不是「可选」，而是「存在即类型错误」——阻止把一次性输入伪装成持久化消息、也阻止给持久化消息抹掉身份。
3. 持久化通道只认「有身份」的消息：`SessionEventMap['user/message']` 的值类型直接是 `UserMessage`（`<HOST>\dsh-session\lib\types\types.d.ts:294`），而 `UserMessage extends MessageBase` 必须有 `id`/`source`；`Session.deriveMessages(): Message[]`（`<HOST>\dsh-session\lib\types\index.d.ts:303`）。一次性输入进不了日志，所以它的类型里就没有身份字段。
